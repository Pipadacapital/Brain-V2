## What this lens sees

The locked four-tool polyglot workspace — Turborepo+pnpm (TS), uv (Python), Buf (proto codegen), at Node 24 LTS / Python 3.13 — is genuinely unusual: most Turborepo monorepos are pure TS; most uv workspaces are pure Python. Brain is both in one root. That junction is where the quiet failures live. The top-level shape being scaffolded now will be read by `pnpm-workspace.yaml`, `pyproject.toml`'s `[tool.uv.workspace]`, `turbo.json`, and `buf.gen.yaml` simultaneously — and those four files have never been stress-tested against each other in the Brain canon. Before this layout becomes load-bearing for every subsequent requirement, the five concerns below need explicit decisions. Three of them (Concerns 1, 2, and 3) could silently pass the scaffold's success contract (`pnpm install` + `turbo` graph + `uv sync` + `buf lint` all resolve cleanly) yet still hide a retrofit trap that would be expensive once 7 services stack on top.

## Concerns

### Concern 1 — Turborepo's `--affected` graph is blind to Python services: the §9.7 "selective per-service deploy" promise is broken for half the stack at this layout

- **Severity:** high
- **Concern:** Turborepo's affected-graph algorithm reads the pnpm lockfile and `package.json` dependency declarations to understand which packages changed and which transitively depend on them. It has no concept of uv workspaces, `pyproject.toml` dependency edges, or Python package boundaries. The three Python services (`ingestion-service`, `analytics-service`, `intelligence-service`) and two Python shared libs (`pylibs/brain_metrics`, `pylibs/brain_clickhouse`, `pylibs/brain_regional`, `pylibs/brain_cost_router`) are not pnpm workspace members and will never appear in Turborepo's package graph. Result: `turbo --affected` will not detect a change in `pylibs/brain_metrics` as a reason to rebuild `analytics-service`, and it will not detect a change in `analytics-service` as a reason to run its Docker build step. Appendix C item 11 ("per-service CI/CD from day one — `turbo --affected` → own ECR → own ArgoCD Application") and §9.7 ("selective per-service deploy from day one") are therefore structurally undeliverable for Python services at this scaffold layout without an explicit workaround.
- **Rationale:** Turborepo's own documentation confirms it operates over pnpm/yarn/npm/bun workspace graphs only; Python uv workspace members are invisible to it. The workaround (shell-script tasks registered as root tasks in `turbo.json`, with manually declared `inputs` globs covering the Python service dirs, so turbo's file-hash cache can detect changes) is valid but must be **explicitly designed in the scaffold** — it does not fall out automatically from `pnpm-workspace.yaml` + `pyproject.toml`. If Aryan's Stage-2 plan creates `turbo.json` tasks only for pnpm packages, Jatin's CI deploy pipeline will silently skip Python service rebuilds on Python-only changesets. This is not hypothetical: the canonical Brain services with the highest change frequency in Phase 1 are `analytics-service` and `ingestion-service` — both Python.
- **Recommended mitigation for Aryan:** The scaffold must include explicit `turbo.json` root tasks (e.g., `docker:build:ingestion`, `docker:build:analytics`, `docker:build:intelligence`) whose `inputs` globs cover the Python service directory tree and their transitive `pylibs/` dependencies. These tasks execute shell scripts (e.g., `uv sync && docker build …`), not `package.json` scripts. This makes Python services visible to `turbo --affected` via file-hash matching, not dependency graph traversal — which is a deliberately weaker guarantee than TS package graph traversal, but it delivers the §9.7 promise. The gap between "graph-aware" (TS) and "file-hash-aware" (Python) affected detection should be documented in the scaffold's `README` so Jatin does not accidentally expect transitive Python dependency tracking that cannot exist at this toolchain boundary.

### Concern 2 — Buf `gen` output landing zone: where generated TS + Python stubs live is not specified in the requirement, and the wrong default creates a circular-import or path-mapping trap

- **Severity:** high
- **Concern:** `buf.gen.yaml` must declare an `out:` directory for each plugin (the TS stubs and the Python stubs). The requirement says `protos/` is the source of truth but does not specify where the generated code lands. Two naive choices cause different retrofit traps: (a) if generated stubs land inside `protos/gen/ts/` and `protos/gen/python/`, then `packages/` (TS consumers) must add a path alias or package reference pointing back into `protos/`, which means pnpm workspace packages import across the `protos/` boundary — a non-standard shape that breaks `tsc --paths` resolution for consumers; (b) if stubs are generated directly into `packages/proto-ts/` and `pylibs/proto-py/` as editable packages, the scaffold must create those packages now (not later) and `buf.gen.yaml` must be wired to those `out:` paths from day one. Either is workable, but the decision must be made at scaffold time. Additionally, the `buf lint` success contract in the requirement validates the proto sources — it does not test that `buf generate` produces output that is importable by TS and Python consumers. A scaffold that passes `buf lint` but has a wrong `out:` in `buf.gen.yaml` will silently defer the circular-import discovery to the first service that actually imports a generated stub.
- **Rationale:** Buf's documentation requires the `out:` field in `buf.gen.yaml` (it is non-optional). The community-standard pattern for polyglot monorepos generates TS stubs into a dedicated pnpm-workspace package (e.g., `packages/proto-ts/`) and Python stubs into a uv workspace member (e.g., `pylibs/proto-py/`), so both sides import a named package rather than a relative path across the `protos/` boundary. If the scaffold creates `protos/` with only `buf.yaml` for linting (no `buf.gen.yaml` at all, or with a placeholder `out:` like `./gen/`), the first developer to run `buf generate` will produce stubs that have no home in the workspace graph, and the `lib-metrics` parity CI check (Appendix C item 5) will silently fail because the Python metrics module cannot import the generated proto types.
- **Recommended mitigation for Aryan:** The scaffold must deliver a working `buf.gen.yaml` (not just `buf.yaml`) that names `out:` paths mapped to real pnpm/uv workspace members. Recommended canonical layout: `out: ../../packages/proto-ts` for the TS connect plugin and `out: ../../pylibs/proto-py` for the Python betterproto/grpc plugin. Both `packages/proto-ts/package.json` and `pylibs/proto-py/pyproject.toml` are stubs created at scaffold time. Committing `buf.gen.yaml` with correct `out:` paths at scaffold time is cheap; retrofitting after 7 services have import paths baked in is expensive. Additionally, the team must decide now whether generated stubs are committed to git or gitignored. The recommended decision is **gitignore generated stubs** (regenerate in CI before build) — committed stubs create merge-conflict noise on every proto change with 7 consumer packages. This decision must be in the scaffold's `.gitignore` from day one.

### Concern 3 — uv workspace root `pyproject.toml` vs. pnpm workspace root `package.json`: the root is a dual-workspace root, and both tools will write lockfiles + environment artifacts that need co-management

- **Severity:** medium
- **Concern:** uv requires the workspace root to have a `pyproject.toml` with `[tool.uv.workspace]` — the root is itself a workspace member. The same directory is also the pnpm workspace root with `package.json` and `pnpm-workspace.yaml`. This means the repo root carries: `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `pyproject.toml` (uv workspace root), `uv.lock`, `.venv/` (uv's default virtual environment, placed at the workspace root), and `node_modules/`. The `.venv/` directory at the root will be picked up by any TypeScript/Node tooling that does naive glob walks (e.g., `tsc --project tsconfig.json` with a wide `include: ["**/*"]`, or ESLint with `lint-staged`). If `turbo.json` input globs are not explicitly scoped to exclude `.venv/` and the uv lock file, `turbo --affected` can produce false-positive cache misses every time `uv sync` regenerates something inside `.venv/`. Similarly, `pnpm-workspace.yaml` must not accidentally glob `pylibs/` or `apps/<python-service>/` as pnpm packages — those dirs contain `pyproject.toml`, not `package.json`, and if pnpm's `packages:` glob matches them, `pnpm install` will fail with an unintelligible error about missing `package.json`.
- **Rationale:** The uv workspace documentation confirms the workspace root must have a `pyproject.toml` and that `uv sync` by default creates `.venv` at the workspace root. The pnpm `packages:` glob in `pnpm-workspace.yaml` must explicitly exclude Python-only directories. The `turbo.json` global `inputs` and per-task `inputs` must explicitly exclude `.venv/**`, `uv.lock`, and `pylibs/**/*.dist-info`. These are all config decisions that need to be in the scaffold, not discovered during the first `pnpm install` after a `uv sync` run.
- **Recommended mitigation for Aryan:** (1) `pnpm-workspace.yaml` must explicitly list TS workspace members or use a glob that excludes Python directories (e.g., `packages: ["apps/web", "apps/mobile", "apps/api-gateway", "apps/core-service", "apps/notifications-service", "apps/lifecycle-service", "packages/*"]` — explicit enumeration preferred over `apps/**` to avoid pnpm accidentally matching Python services). (2) Root `.gitignore` must include `.venv/`, `*.egg-info/`, `__pycache__/`, and `uv.lock` should be committed (uv's own guidance is to commit the lockfile for reproducibility — equivalent to `pnpm-lock.yaml`). (3) `turbo.json` global `inputs` must exclude `.venv/**`. (4) Root `tsconfig.json` `exclude` must include `.venv`, `pylibs`, and `apps/<python-service>` directories to prevent TypeScript from attempting to type-check Python service directories.

### Concern 4 — Version pinning is not fully specified: five tools, five pinning mechanisms, zero of them cross-referenced in the requirement

- **Severity:** medium
- **Concern:** The requirement lists "locked, pinned versions" as a deliverable in the working root toolchain config, but the requirement text only cites "Node 24 LTS, Python 3.13" without specifying which of the five tools' pinning files must exist and what exact version is used for each. The five tools requiring explicit pinning in the scaffold are: (1) Node.js — `.node-version` or `.nvmrc` + `package.json` `engines.node`; (2) pnpm — `package.json` `packageManager` field (Corepack, e.g., `"pnpm@9.x.x"`); (3) Python — `.python-version` (for pyenv/mise/uv's own version resolution) + `pyproject.toml` `requires-python = ">=3.13,<3.14"`; (4) uv — `pyproject.toml` `[tool.uv] required-version = ">=0.x.x"` or a pinned version in the Dockerfile/CI; (5) Buf — `buf.yaml` `version: v2` (or explicit CLI version in CI). If any of these five pinning files are absent from the scaffold, a teammate (Vikram on Node, Maya on Python) running `corepack use` or `mise install` without the pinning files gets an undeclared version and the "toolchain resolves cleanly" success contract is a lie — it resolved for one person on one machine.
- **Rationale:** The "pnpm install resolves cleanly" success contract requires that `package.json`'s `packageManager` field is set (Corepack reads it); without it, a developer gets whatever pnpm is globally installed. Similarly, `uv sync` with no `.python-version` file uses the system Python, which may not be 3.13. Node 24 is LTS as of 2025 but `.node-version` or `engines.node` being absent means CI can silently run Node 22 if the runner image defaults to it.
- **Recommended mitigation for Aryan:** The scaffold must deliver all five pinning artifacts: `.node-version` (e.g., `24`), `.python-version` (e.g., `3.13`), `package.json` `"packageManager": "pnpm@9.x.x"` with the exact pnpm patch version, `pyproject.toml` `requires-python = ">=3.13,<3.14"`, and `buf.yaml` `version: v2`. A `README.md` at the repo root (or a `TOOLCHAIN.md`) listing the exact versions and the single `mise install` or manual install command to bootstrap a new machine is cheap insurance against the "works on my machine" failure mode at the first team onboarding.

### Concern 5 — The metric-registry parity CI check (`packages/lib-metrics` vs `pylibs/brain_metrics`) has no execution path in the scaffold's success contract

- **Severity:** low
- **Concern:** Appendix C item 5 states: "Metric registry with TS-to-Python parity; CI enforces parity." Blueprint §9.1 places the pair at `packages/lib-metrics` and `pylibs/brain_metrics`. The scaffold creates these as `.gitkeep` homes. The requirement's success contract (`pnpm install` + `turbo` graph + `uv sync` + `buf lint` all resolve) does not include the parity check script (`tools/generate-metrics-registry.sh` per §3 of the Blueprint). This is appropriate for a skeleton, but the scaffold must at minimum create the `tools/` directory with a stub `generate-metrics-registry.sh` and wire it as a `turbo.json` root task (`check:metrics-parity`), even if the script body is a placeholder that exits 0. If the CI parity check script has no home in the scaffold, the first metric definition added by Maya in `analytics-service` will have no failing CI signal to enforce that a matching Python definition exists in `pylibs/brain_metrics`. The parity invariant will be quietly violated on the first real metric commit.
- **Rationale:** The scaffold's explicit job is to give every day-one non-negotiable a home (from Rohan's Stage 1 review). A home without a CI wiring point is incomplete — the `lib-metrics` directory exists but there is nothing in `turbo.json` that will fail if parity is broken. This is low severity because no metrics exist yet and the script stub body is trivial, but it is the kind of "cheap now, brutal to retrofit" item Appendix C was written to prevent.
- **Recommended mitigation for Aryan:** Create `tools/check-metrics-parity.sh` as a stub (exits 0 with a `TODO: implement` comment) and add a `check:metrics-parity` root task in `turbo.json` with `inputs: ["packages/lib-metrics/**", "pylibs/brain_metrics/**", "tools/check-metrics-parity.sh"]`. This costs ~10 lines and ensures the CI wiring point exists before the first real metric lands.

## Recommendations

1. **Aryan's Stage-2 plan must explicitly resolve Concerns 1 and 2 before Aryan writes a single line of scaffold code.** Concern 1 (Turborepo blind to Python services) and Concern 2 (Buf `gen` output landing zone + gitignore decision) are structural decisions that cannot be patched after the layout is load-bearing. Specifically: (a) decide the Python `turbo.json` task strategy (root tasks with `inputs` globs vs. a Makefile wrapper invoked by a turbo shell task); (b) decide the generated stubs home (`packages/proto-ts/` + `pylibs/proto-py/` as stub workspace members vs. `protos/gen/`); (c) decide generated stubs gitignored vs. committed. Record both decisions in a `DECISIONS.md` at the repo root so Jatin (CI/deploy) does not have to reverse-engineer them from config files.

2. **The scaffold's verifiable success contract should be tightened.** The current contract (`pnpm install` + `turbo run --dry` graph + `uv sync` + `buf lint`) passes even if Concerns 3, 4, and 5 are unaddressed. Aryan should add two more checks to the scaffold's acceptance criteria: (a) `turbo run check:metrics-parity` exits 0 (the stub); (b) `python -c "import brain_metrics"` resolves (confirms `pylibs/brain_metrics` is a valid uv workspace member). These two additions make the scaffold fail-loud on misconfiguration rather than silently appearing healthy.
