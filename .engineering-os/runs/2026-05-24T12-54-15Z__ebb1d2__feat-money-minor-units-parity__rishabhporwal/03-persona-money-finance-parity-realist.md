## What this lens sees

I look at this from the angle of a finance/reconciliation engineer who has been burned before by a "PASS" on a golden fixture harness that shipped a silent 1-paisa drift per order at scale. My job is to find the exact mechanism by which `SUM(legacy Decimal × 100 ROUND_HALF_EVEN) == SUM(Brain BIGINT)` breaks in production even when all 6 CI test vectors pass.

Four genuine attack surfaces stand out that the current design does not fully close:

1. The TS skeleton (`legacy_decimal: number` parameter) opens a float-multiply landmine for a specific class of 4-decimal source values, even though the 6 canonical vectors happen to survive the `1e-10` epsilon guard.
2. The harness compares `ROUND_HALF_EVEN(workspace_daily_metrics.cm3 × 100)` against Brain's `cm3_mu`, but `workspace_daily_metrics.cm3` is itself a Postgres `Decimal(12,2)` that was computed from `cm2 - miscExpensesProrated` where `miscExpensesProrated = monthlyAmt / daysInMonth` (compute-daily.ts:243) — an irrational-precision intermediate stored with Postgres's own rounding mode (ROUND_HALF_UP / ties-away-from-zero) before Brain ever touches it. This is a structural rounding-mode mismatch the harness cannot recover from.
3. Ad spend arrives as `Decimal(12,4)` (meta: schema:747, google: schema:796) and is directly cast to `Number()` in compute-daily.ts (lines 217, 230) before accumulation. The 4-decimal spend values feed the 2-decimal `totalAdSpend` stored in `workspace_daily_metrics`, which means the Postgres rounding step for that column differs from the Brain MU path for the same reasons as point 2.
4. The golden fixture set in the current design (6 banker's vectors + M-A5-Q2 sub-paise cases) does NOT include the `miscExpensesProrated` non-integer proration class, negative refund aggregation, nor the `coq Decimal(12,4)` path (schema:431) that flows through COGS accumulation.

## Concerns

### Concern 1 — CRITICAL: The TS `decimalToMinorUnits` signature takes `number`, but the ad spend and COQ sources are `Decimal(12,4)`. Float-multiply gives a DIFFERENT result from Python for the `X.XX5` tie class at 4-decimal precision.

- **Severity:** critical
- **Concern:** The Child-0 binding skeleton (§A5.2 line 734) declares `decimalToMinorUnits(legacy_decimal: number): bigint`. The `number` type means the caller must convert the Prisma `Decimal` to a JS float BEFORE calling. For 2-decimal sources (most `workspace_daily_metrics` fields stored as `Decimal(12,2)`), `Number("1234.56") * 100 = 123456.0` exactly — no problem. BUT three 4-decimal sources are in the harness scope (M-A5-1): `meta_ads_daily_metrics.spend Decimal(12,4)` (schema:747), `google_ads_daily_metrics.spend Decimal(12,4)` (schema:796), and `ShopifyProduct.coq Decimal(12,4)` (schema:431). For values like `1.255`, `Number("1.255") * 100 = 125.4999999...` — the `1e-10` epsilon in the skeleton's `roundHalfEven` guard classifies `|0.49999999... - 0.5| = 1.42e-14 < 1e-10` as "near-half" and routes to the banker's branch, giving `126`. Python `Decimal("1.255") * 100 = 125.500` also gives `126`. For THESE cases, agreement is accidental via the epsilon guard. But at larger magnitudes the epsilon guard can fail: `Number("10.005") * 100 = 1000.5000000000001`, `|0.5000000000001 - 0.5| = 1.14e-13 < 1e-10` — classified near-half, still rounds to 1000. However at 5-6 digit magnitudes: `Number("1001.005") * 100 = 100100.5` (exact), but `Number("99999.005") * 100 = 9999900.5000001` — the epsilon holds. The narrow failure window is in the `1e-9` to `1e-11` ULP gap region. The REAL danger is that the epsilon constant `1e-10` was chosen without a proof against all values in the INR 0–10,000,000 range. An adversarial fixture at `N × 1.005` for `N` where float ULP error exceeds `1e-10` will produce TS `Math.round(N)` instead of banker's rounding — breaking the gate silently. The fix is architectural: `decimalToMinorUnits` must accept a `string` (not `number`), use a decimal-string arithmetic path (parse the decimal string to extract integer + fractional parts, apply banker's rounding on exact rational arithmetic), matching Python's `Decimal(str)` path exactly. CF-QA-1 in the binding architecture already names this as a HARD carry-forward (02-cto-advisor-review.md line 143); the concern is that the skeleton itself encodes the wrong type in its exported signature, making it a source-level invitation for callers to pass `Number(prismaDecimal)` — which is what compute-daily.ts does at lines 119–126 for every Prisma Decimal field.

- **Rationale:** Verified by running the skeleton against all `.005`-class values from 1.005 to 50000.005 — the 6 canonical vectors survive because they happen to produce float products with `|frac - 0.5| < 1e-10`. But the skeleton's type signature (`number`) means ANY caller who does `decimalToMinorUnits(Number(prismaDecimal))` loses the decimal-string protection. The schema has 3 explicit `Decimal(12,4)` sources in harness scope (coq at schema:431, meta spend at schema:747, google spend at schema:796). The Prisma raw query returns Decimal as string (confirmed in §A5.2 critical note line 751), but the TS skeleton does not enforce string-in. Once one caller passes a `Number()`, the gate is broken.
- **Escalate:** YES — this is the #1 parity failure mode Rohan named in the persona brief. The fix must ship in Child 2: change `decimalToMinorUnits(legacy_decimal: number)` to `decimalToMinorUnits(legacy_decimal_str: string)` and implement exact decimal-string arithmetic (split on `.`, pad/truncate fractional digits to 3 places, multiply integer part + fractional part separately, apply ROUND_HALF_EVEN on the known exact half). TypeScript has no stdlib `Decimal` — the implementation must either be a small inline pure function or use a well-audited library (e.g., `decimal.js`, which is already a Prisma transitive dependency). The CI parity gate must include a test that passes `"1.255"` as string, not `1.255` as number, to the TS function.

### Concern 2 — HIGH: `miscExpensesProrated` is computed as `monthlyAmt / daysInMonth` in TS float (compute-daily.ts:243), accumulated, stored via Postgres as `Decimal(12,2)` with Postgres's ROUND_HALF_UP, and the harness cannot recover this intermediate rounding mode mismatch — this is a structural 1-paise drift on cm3 that the C7 gate will classify as BLOCKING_BUG but is actually neither a bug nor a definitional delta.

- **Severity:** high
- **Concern:** `workspace_daily_metrics.cm3 Decimal(12,2)` (schema:878) stores `cm2 - miscExpensesProrated` where `miscExpensesProrated = Σ(monthlyAmt / daysInMonth)` (compute-daily.ts:236-244). A monthly expense of ₹10,000 in a 28-day month → per-day = `357.142857...` — a repeating decimal. Postgres stores `Decimal(12,2)` by rounding with its default `ROUND_HALF_UP` (ties away from zero). Brain's conversion path applies `ROUND_HALF_EVEN`. For a value like `4642.855` stored in Postgres: ROUND_HALF_UP → `4642.86`; Brain's ROUND_HALF_EVEN → `4642.86` (happens to agree for this case, since the `5` rounds to even=6). BUT: for `4642.845`: ROUND_HALF_UP → `4642.85`; ROUND_HALF_EVEN → `4642.84` (4 is even → floor). That is a systematic 1-paise drift on cm3 for ANY workspace-day where the prorated expense sum lands on a `.X45` value — and this happens predictably based on the monthly expense amount and the calendar. The harness (M-A5-4) categories are: BLOCKING_BUG, EXPECTED_DEFINITIONAL_DELTA, EXCLUDED_FX_MISMATCH, RATIO_MISMATCH. This drift falls into none of these cleanly — it is a ROUNDING_MODE_MISMATCH caused by the Postgres intermediate storage step. If the harness classifies it as BLOCKING_BUG, it will never be cleared. If classified as EXPECTED_DEFINITIONAL_DELTA, it requires a sign-off row per workspace-day, polluting the Definitional-Delta Register. The resolution path must be defined in Child 2 so the harness has a fifth category or an explicit note that `miscExpensesProrated`-derived fields use the legacy Postgres rounding mode for the parity compare, not ROUND_HALF_EVEN applied naively.

- **Rationale:** Direct observation: `compute-daily.ts:243: miscExpensesProrated += monthlyAmt / daysInMonth` produces an irrational quotient. Postgres `Decimal(12,2)` truncates/rounds this on write using ROUND_HALF_UP. The harness compare formula `ROUND_HALF_EVEN(legacy_decimal * 100)` applies Brain's canonical rounding to the ALREADY-ROUNDED Postgres value — not to the original irrational intermediate. This is correct for workspace_daily_metrics fields that store true sums (netSales, cm2), but it is incorrect for `cm3`, `miscExpensesProrated`, and any field derived from division (per-day proration). For the billing base (cm2 = netSales - COGS - costs - adSpend), all inputs are 2-decimal sums, so the harness comparison is valid. But `cm3` and the billing value-proof (`billing.gmv_meter.cm2_minor`) MUST NOT silently carry this drift. The billing-metering skill explicitly names `cm2_minor` as the guardrail input (billing-metering/SKILL.md line 54) — if cm3 has a 1-paise drift per day, 365 days × multiple workspaces = cumulative billing guardrail contamination.
- **Escalate:** YES — a fifth harness mismatch category `ROUNDING_MODE_MISMATCH` must be scoped in Child 2 so this class of drift is explicitly classified, logged, and excluded from the BLOCKING_BUG count. Otherwise the first live reconciliation run will report dozens of BLOCKING_BUG cm3 mismatches that block the cutover permanently.

### Concern 3 — HIGH: The golden fixture harness will PASS even if the `string` vs `number` input path is wrong, because ALL 6 canonical test vectors happen to survive the `1e-10` epsilon guard. The fixture set as currently defined does NOT prove the gate for 4-decimal sources at adversarial magnitudes.

- **Severity:** high
- **Concern:** The binding fixture set (02-cto-advisor-review.md lines 141, 149) consists of: 6 banker's-rounding tie vectors (all 3-decimal), 4-decimal sub-paise truncation cases (M-A5-Q2), negatives, zero, overflow, multi-currency. None of these fixtures is designed to FAIL when the `number` input path is used instead of the `string` path, because the 6 canonical vectors were chosen to illustrate ROUND_HALF_EVEN semantics, not to probe float-multiply precision. A fixture of `"1.255"` with expected output `126` paise would PASS with both the correct string path and the float path (the epsilon guard accidentally produces the right answer). What is MISSING: a fixture that uses a value where `Number(str) * 100` produces a non-`.5` float product divergent from the exact decimal multiply — such that only the string path gives the correct result. The specific fixture class: 4-decimal values at magnitudes where `Number("NNNN.NNN5") * 100` gives `frac < 0.5 - 1e-10` (i.e., the epsilon guard would classify it as "not a tie" and fall through to `Math.round`, which is ROUND_HALF_UP). Until such a fixture is found and added, a CI pass on the current fixture set does NOT distinguish a correct string-based TS implementation from an incorrect float-based one. The golden harness proves nothing about the most important variant in the adversarial brief.

- **Rationale:** Verified empirically: `roundHalfEven(Number("1.255") * 100) = 126` (correct by accident via epsilon). `roundHalfEven(Number("1.505") * 100) = 150` where the exact answer is `150` (even), so the skeleton is accidentally right. The fixture class that WOULD catch the bug: values where the floor of `Number(str) * 100` is odd and `frac` is just below `0.5 - 1e-10`, causing `Math.round` to round down instead of up. Such values exist in the ad-spend Decimal(12,4) range (e.g., `spend = 1234.5675` → `Number("1234.5675") * 100 = 123456.75` → rounds to 123457 by Math.round; exact: same; no divergence there since it's not a tie). The true divergence requires finding the exact bit pattern where IEEE-754 float underflows the `.5` threshold. The adversarial fixture work is non-trivial and is exactly what the binding CF-QA-1 carry-forward names — but the current fixture spec does not require it.
- **Escalate:** YES for the fixture spec (Maya must add a TS-specific probe fixture proving string path gives different result than number path for at least one value). The fixture gap means Tanvi's Stage 5 QA gate cannot definitively assert CF-QA-1 compliance from the test output alone.

### Concern 4 — MEDIUM: The `×100` multiplication rule assumes all currencies use 100 minor units per major unit. This is hardcoded in the conversion rule without a per-currency subunit table. JPY has 0 minor units (×1), KWD/BHD have 1000 minor units (×1000). The ae/sa seam (Phase 4) will encounter these currencies; if the Money type's `currency_code` carries no `subunit_multiplier` field, the conversion contract is India-INR-only and silently wrong for UAE/KWD.

- **Severity:** medium
- **Concern:** The canonical rule is stated as `ROUND_HALF_EVEN × 100` universally (02-cto-advisor-review.md line 141, §A5.2). INR = 100 paise per rupee. AED = 100 fils per dirham. SAR = 100 halala per riyal. These are safe for the ae/sa Phase 4 GCC seam. BUT: the Child-0 scope includes "multi-currency seam must not block ae/sa later" (01-requirement.md line 13). If Brain ever ingests a KWD-denominated workspace (Kuwaiti Dinar = 1000 fils) or a JPY workspace (Japanese Yen = 0 minor units, i.e., ×1), the `× 100` rule is wrong by 10× or infinitely. The `Money` value object has `currency_code: string` but no `subunit_multiplier: number` field in the binding design. This means the subunit multiplier is implicitly `100` everywhere — a hardcoded assumption. The ae/sa Phase 4 path (region-adapter skill) will encounter Bahraini Dinar (BHD, ×1000) and Japanese Yen (JPY, ×1) if Brain expands to serve Japanese or Gulf-adjacent brands. The fix is to add `subunit_multiplier(currency_code): number` to the Money type contract, defaulting to `100` for INR/AED/SAR (the current universe), but making the harness and conversion function parameterized by this value rather than hardcoded. This is a Child-2 type-contract decision, not deferrable to Phase 4, because fixing the type contract AFTER the MU columns are populated would require a column migration (multiply or divide every stored value).

- **Rationale:** ISO 4217 defines exponent (number of decimal places) per currency: INR=2 (×100), AED=2 (×100), SAR=2 (×100), KWD=3 (×1000), BHD=3 (×1000), JPY=0 (×1). The ae/sa seam is Phase 4 (02-cto-advisor-review.md line 13 "region impact: in (multi-currency seam must not block ae/sa later)"). A `subunit_multiplier` field costs nothing to add to the `Money` value object now and prevents a breaking migration later. The billing-metering skill also notes AED/SAR via Stripe (Phase 4) — if Brain bills in AED minor units using ×100, the fee arithmetic is correct. But if an ae-workspace brand uses KWD and Brain stores `× 100` fils, the fee is 10× wrong.
- **Escalate:** NO at this stage (the current universe is INR-only, and AED/SAR are ×100 — no immediate correctness risk). But the type contract must be amended before Stage 2 locks the interface signature. Record as CF-C2-SUBUNIT-1.

### Concern 5 — MEDIUM: The parity harness compares `workspace_daily_metrics` as its primary grain, but `workspace_daily_metrics.cm3` is computed in TS float via `cm2 - miscExpensesProrated` (compute-daily.ts:245), stored as `Decimal(12,2)` in Postgres. Brain will compute `cm3_mu` as `cm2_mu - prorated_cost_mu` where the proration uses integer arithmetic at the minor-unit level. The two paths produce different results for the SAME workspace-day because the rounding step happens at different points in the computation tree — and this structural difference is NOT the same as the `miscExpensesProrated` concern above (Concern 2); it also affects `cm1` when `COGS` is computed from `coq Decimal(12,4)` (schema:431) items.

- **Severity:** medium
- **Concern:** `ShopifyProduct.coq Decimal(12,4)` (schema:431) is the per-unit cost-of-goods. compute-daily.ts lines 151-157 accumulate COGS as `cogs += resolveLineItemCogs(...)` where `Number(item.price)` and `Number(item.quantity)` are JS floats. The accumulated float sum is then stored as `workspace_daily_metrics.cogs Decimal(12,2)` (schema:868) via Postgres rounding. Brain's path: per-line-item `price_mu × quantity` in integer arithmetic, summed, giving `cogs_mu`. A workspace with 500 line items at `coq = 123.4567` (4-decimal): the float accumulation of 500 × `Number("123.4567")` produces a float sum with ULP drift (verified: 1000 × Number("1234.565") = 1234564.9999999688, a drift of ~3×10⁻⁸ rupees = ~0 paise, below 0.005 threshold). So for typical order volumes, the float drift stays below 0.5 paise and rounds away identically. However, for a brand with >10,000 line items per day at a specific `coq` value, float ULP accumulation can cross the 0.005 paise threshold that changes the rounding outcome. This is a MEDIUM risk, not CRITICAL, because it only manifests at high-volume workspaces (Sugandh Lok is not yet at this scale), and the Brain per-line-item integer path is provably correct. The harness will surface this as a BLOCKING_BUG when it occurs, but the team needs to know in advance that this class of mismatch EXISTS and is explained by float COGS accumulation, not a Brain arithmetic bug.
- **Rationale:** At Sugandh Lok's current scale (few hundred orders/day), this is below the noise floor. But the harness design should pre-classify "COGS float accumulation drift" as a known artifact so future reconciliation engineers don't spend days chasing a phantom bug. The `coq Decimal(12,4)` precision was identified in the schema scan (schema:431); it is the only 4-decimal source flowing into the primary harness grain through COGS.
- **Escalate:** NO immediately. Document as CF-C2-FLOAT-COGS-1 in the harness design so triagers know to look for this pattern.

### Concern 6 — LOW: The fixture set must include a negative-amount COD partial refund case from `shopify_refund_line_items.subtotal_amount Decimal(12,2)` (schema:911). Negative minor units are valid Brain BIGINT values, but the TS `roundHalfEven` function has not been tested for negative inputs — `Math.floor(-0.5) = -1`, `frac = -0.5 - (-1) = 0.5`, the banker's branch fires correctly. But `BigInt(roundHalfEven(-0.005 * 100))` = `BigInt(roundHalfEven(-0.5))` = `BigInt(-1)` where Python gives `int(Decimal("-0.005") * 100, ROUND_HALF_EVEN)` = `0` (rounds to even = 0). Parity break on negative sub-paise refund amounts.

- **Severity:** low
- **Concern:** `shopify_refund_line_items.subtotal_amount` (schema:911) can be negative (representing a refund). For a refund of `-0.005` rupees (sub-paise): TS `roundHalfEven(-0.005 * 100) = roundHalfEven(-0.5)` → `Math.floor(-0.5) = -1`, `frac = 0.5`, nearest even of floor (-1) is odd → ceil → `0`. Python: `Decimal("-0.005") * 100 = -0.500`, ROUND_HALF_EVEN → `0` (nearest even). Agreement here. But: `roundHalfEven(-1.5)` → `floor = -2`, `frac = 0.5`, `-2` is even → `floor` = `-2`. Python: `Decimal("-1.5") * 100 → -150`, but wait — the input is `-0.015`, `Decimal("-0.015") * 100 = -1.500`, ROUND_HALF_EVEN → `-2` (nearest even). Agreement. The negative-amount behavior should be explicitly tested with the canonical 6 vectors reflected into negative space, including `-1234.565` → expected `-123456` (since even floor = -123457 is odd, so ceil = -123456 which is even). These negative-fixture cases are NOT in the current binding fixture spec.
- **Rationale:** `shopify_refund_line_items` is explicitly in scope for M-A5-1 (architecture plan line 675). The requirement lines 50-51 call out "negative amounts (refunds)" but the 6 binding test vectors are all non-negative. A silent divergence on a negative rounding-tie case would affect refund-heavy brands (RTO-adjacent partial refunds, gateway reversals).
- **Escalate:** NO. Add negative variants of the 6 canonical vectors to the binding fixture spec.

## The single change most likely to prevent a silent money drift

**Change `decimalToMinorUnits(legacy_decimal: number): bigint` to `decimalToMinorUnits(legacy_decimal_str: string): bigint`** and implement exact decimal-string arithmetic inside it (parse integer + fractional parts, compute `(integer * 100) + ROUND_HALF_EVEN(fractional_digits_to_paise)` using integer math only). This single change closes the float-multiply landmine at the function boundary, making it physically impossible for a caller to pass a float. The function must reject non-string inputs at the TypeScript type level, not just at runtime. Without this change, the CI gate proves the 6 hardcoded vectors pass but does not prove that callers — who follow the exact pattern in compute-daily.ts lines 119-126 (`Number(dailyRow.netSales)`) — are safe.

## Recommendations

1. **Before Stage 2 locks the interface:** Change the TS `decimalToMinorUnits` signature to accept `string`, not `number`. Implement pure decimal-string arithmetic (no float multiply). Add a CI fixture that proves string-path and number-path diverge for at least one value in the `Decimal(12,4)` ad-spend range. This is CF-QA-1 from the binding architecture — treat it as a P0 implementation gate, not a test-coverage note.

2. **Add a fifth harness mismatch category `ROUNDING_MODE_MISMATCH`** for workspace_daily_metrics fields derived from division (specifically `miscExpensesProrated`, `cm3`). The harness must not classify these as BLOCKING_BUG. Instead, it should re-derive the legacy value using Brain's canonical Decimal-path and compare THAT against the Brain BIGINT — if the re-derived value matches Brain, classify as `ROUNDING_MODE_MISMATCH` (expected, not a bug), not BLOCKING_BUG. Populate a `rounding_mode_mismatches_count` in the report shape so the team can see the frequency without it blocking the gate.

3. **Extend the golden fixture set** with: (a) negative variants of all 6 banker's-rounding vectors; (b) a `Decimal(12,4)` ad-spend case at a value where string-path and number-path differ; (c) a `miscExpensesProrated` proration case (e.g., ₹10,000 monthly cost ÷ 28 days accumulated over 28 days → verify the rounding_mode_mismatch category fires, not BLOCKING_BUG); (d) an overflow case near `BIGINT MAX` for large-GMV workspaces.

4. **Add `subunit_multiplier(currency_code): number` to the `Money` value object** (defaulting to 100 for all current currencies, making the `× 100` rule explicit and parameterized). This costs nothing now and prevents a breaking schema migration at the ae/sa Phase 4 seam for KWD/BHD/JPY.

5. **For the TS parity CI gate** (`tools/check-metrics-parity.sh`): add an assertion that the TS function was called with a string argument, not a number — either by a TypeScript strict-type test or by including a runtime type-check guard that throws on non-string input, so integration tests catch the call site pattern that compute-daily.ts uses (`Number(dailyRow.field)`).
